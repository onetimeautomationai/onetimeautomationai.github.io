The Blueprint

How I Build AI Automations

Score it before you build it. Then six steps, in order.

An automation is a workflow you already do in real life. The only thing that changed is that Claude can now work the apps you work: email, calendar, Chrome, your files. So the question stopped being "can this be automated." It became "should this one be."

Most people skip that second question and build the thing. Then they maintain it forever.

Part 1

The 80% test

Before any building, one gate.

Run the workflow by hand, once, slowly. Write down every step as you do it.

Not from memory. From the actual run. Memory compresses the annoying parts, and the annoying parts are where automations break.

For each step write what happens, which app it happens in, and whether a decision gets made. Then score every step as one of three:

ScoreMeaning
ClaudeClaude can do this end to end without me watching
MeNeeds a judgment call, an approval, or a login only I can pass
NeitherNobody can do this reliably yet, including me

Count the Claude steps. Divide by total steps.

Under 80%, do not build it.

At 50% automation you still show up for the whole workflow. You just show up later, in the middle, with less context about what already happened. You added a handoff and called it a system.

Half-automated work is often slower than the manual version, because now you are doing the work and auditing a machine. At 80% and up, the workflow runs without you and you are approving an outcome instead of producing one.

Three things that quietly sink the count:

  1. A judgment step you cannot write down. If you cannot explain the rule to a smart new hire in two sentences, Claude cannot own it either. Score it Me.
  2. A login nothing can pass. Two-factor, a portal with no API, a system that logs you out hourly. Score it Me, and do not pretend otherwise.
  3. A step where being wrong is expensive. Money moves, a client sees it, something gets deleted. That step stays Me even when Claude could technically do it. Automate the work, not the liability.

Do not round up. The test only protects you if you let it fail.

Here is the prompt I use to run Part 1 with Claude instead of on paper:

Paste into Claude Code, Cowork, or Codex 
I want to decide whether to automate a workflow.

The workflow: [describe it in one or two sentences]

Interview me one question at a time until you have every step
I actually take, which app each step happens in, and what
decision I make at each step. Do not guess a step. Do not
move on until my answer is specific.

When you have the full list, output a table with one row per
step and a column scoring each step as CLAUDE, ME, or NEITHER,
using these definitions:

CLAUDE   = you could do this end to end with no human watching
ME       = needs judgment I cannot write as a rule, a login
           nobody can script, or a mistake that costs real money
NEITHER  = nobody can do this reliably yet

Then give me the percentage of steps scored CLAUDE, and a
one-line verdict: BUILD if 80% or higher, DO NOT BUILD if under.

If it is under 80%, tell me which specific steps to change to
get it over the line. Do not soften the verdict to be nice.
Part 2

The build SOP

Only run this after the test says build.

Step 1 Decide four things before you write anything

Write these down. Four lines is enough.

  • Trigger. What starts it. A time of day, an email landing, a file appearing, you typing one word. If you cannot name the trigger you do not have an automation, you have a script you will forget to run.
  • Memory. Where the state lives between runs. A file, a spreadsheet, a small database. Something that survives the tab closing. Without it, every run starts from zero and you get duplicate emails, repeated work, and no way to prove what already happened.
  • Failure. What it does when it breaks, and who finds out. An automation that fails loudly costs you five minutes. One that fails silently costs you a client.
  • The handoff. Which steps stay yours, and how the automation hands them to you. Your Me steps from Part 1 go here.

Step 2 Write down what "done" means, before you build

Three to six things you can check yes or no.

Checkable

"It sends by 7am." "It never emails the same person twice." "It writes a row for every run, including failed ones."

Not checkable

"It works well." "The output is high quality." "It saves me time."

If you cannot check it yes or no, it does not belong on the list. This list is what you grade the build against later, so writing it after the build defeats the point. You will write criteria the build already passes.

Step 3 Build the smallest version that does the real job

Version zero. The core loop, nothing else. Every other idea goes on a second list called Later, one line each, with why it is waiting. Not deleted. Scheduled.

Most automations die because version one tried to be version five. The retry logic, the dashboard, the four edge cases nobody has hit yet, the config file for settings you will never change. Cut all of it. You can add anything to a system that runs. You can add nothing to a system that never shipped.

Step 4 Run it. Actually run it.

Not read the output and nod. Not ask Claude if it worked.

Take your list from Step 2 and go one row at a time. Check each one against a real run with real data. Write the evidence next to each row: the file exists, the count matches, the email arrived at 6:58.

A row you cannot check is a row that failed. A row that failed is a build that failed. Fix it or say out loud that it is broken. "Looks right" is how automations get trusted for six weeks before anyone notices they stopped working in week two.

Step 5 Save one good run

Keep one real input and the exact output it produced. Put it somewhere you will find it.

That pair is your baseline. Every time you change the automation later, run the same input and compare against it. This is the difference between improving a system and randomly editing it. You will change something small in month three and break something you forgot existed, and this is the only cheap way to catch it.

If you do not have a verified-good run yet, the first one that passes Step 4 becomes the baseline.

Step 6 Leave the system behind

Turn the finished build into a skill, so the next automation starts from this one instead of from scratch.

That is the compounding part. One automation saves you a workflow. A skill for building automations saves you every workflow after it.

The short version

  1. Run it by hand and write down every step
  2. Score each step Claude / Me / Neither
  3. Under 80% Claude, walk away
  4. Name the trigger, the memory, the failure, and the handoff
  5. Write what done means, in yes-or-no terms, first
  6. Build version zero only
  7. Run it against that list with real data
  8. Save one good run as your baseline
  9. Turn it into a skill

Steps 1 through 3 are the ones people skip. They are the ones that decide whether you end up with a system or a maintenance job.
